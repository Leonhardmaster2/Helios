# Work log — 25 October 2026

## Objective

Extend Helios with the first scene that has a **Sun entity**, using the existing procedural
cube-sphere planet renderer, and leave a running, documented build by the afternoon. Side issues
were allowed to be fixed in parallel.

## Delivered

### `helios_solar_system` — a new Diligent/Vulkan lab

The Sun and the eight planets are bodies on the planet LOD lab's `PlanetPatchRenderer`:

- **The Sun is a real body**: `PlanetBody.star = true`, radius 695,700 km, a new emissive branch in
  `shaders/planet_patch.slang` with Eddington limb darkening, drifting granulation and a
  screen-space limb fade. It is not a light, billboard, lens flare or skybox.
- **Planets** are the same `PlanetBody` type with per-world presets: Mercury, Venus, Earth, Mars,
  Jupiter, Saturn, Uranus and Neptune.
- **Rotation**: each body spins at its sidereal rotation period (retrograde where the period is
  negative); the camera and sun direction are rotated into the body-fixed frame. Axial tilts are
  not applied yet.
- **J2000 positions** come from NASA NSSDCA mean elements plus a two-body Kepler solver
  (`solar_system_data.hpp`). The rows were checked against JPL Horizons DE441: inner planets
  within 2–20 arcseconds at J2000.
- **Per-body LOD**: each body owns a `QuadtreeLodSelector`; captures settle until a still camera
  causes no more splits/merges.
- **Camera**: orbit the Sun or follow any planet, with a sunward reference frame so a planet's
  default view is its lit hemisphere.
- **Overlay**: colour-coded orbit lines and labels, drawn with ImGui in the window and rasterised
  into the PNG with the existing 4x6 font for headless captures.
- **Anti-aliasing**: the 3-D scene renders at 4× for captures up to 1080p and 2× for the interactive route
  (1x/2x/4x selectable); `shaders/solar_resolve.slang` / `solar_resolve4.slang` perform an exact
  integer-load box resolve into the output before the HDR display chain. This avoids the
  shared post chain's point-sampled scene lookup and gives the Sun/planet limbs four or sixteen samples per
  output pixel. The limb fade in the star shader is a second, screen-space guard.
- **Routes**: interactive window, `--capture` (windowless), `--smoke-frames` (hidden-window smoke).
- **Reproducibility**: `--report PATH.json` writes the schema, commit, adapter, date, camera,
  display scales, body positions/radii, metrics and validation count for a capture.

## How it is put together

| File | Role |
|---|---|
| `solar_system_data.hpp` | J2000 elements, physical data, Kepler solver (header-only, no GPU types) |
| `solar_system.hpp/.cpp` | `PlanetBody` presets, names, positions, display radii |
| `solar_system_stage.hpp/.cpp` | multi-body LOD, camera, HDR scene targets, 2x box resolve, post chain |
| `main.cpp` | SDL window, capture, orbit/label overlay, ImGui panel |
| `shaders/solar_resolve.slang` | 2x2 box downsample with integer `Load`s |
| `shaders/planet_patch.slang` | new star branch (limb darkening + granulation + limb coverage) |

The scene is rendered into an `RGBA16F` target at `output × 2`; a fullscreen pass averages 2x2
source texels with integer loads into a 1x `RGBA16F` target; `HdrPostChain` then applies glare,
exposure and ACES. `supersample = 1` bypasses the resolve and uses the scene directly.

## Issues found and what was done

1. **First capture was black.** `PlanetPatchSettings.max_render_distance_m` defaults to 2e9 m, a
   planet-local limit; at 6 AU every patch was distance-culled. Set it to 2e14 m for the
   solar-system stage.
2. **Earth close-up was the night side.** The camera frame used world azimuth; a planet's default
   view could be unlit. The camera now measures azimuth around the body's sunward direction.
3. **Supersampling did not visibly anti-alias.** The shared `HdrPostChain` samples its HDR scene
   through a combined image sampler that behaved as point sampling when the scene and output
   resolutions differed; a 2x scene was being point-copied. Added the explicit integer-load box
   resolve (`solar_resolve.slang`) in this lab instead of changing the shared chain. The existing
   labs still use the shared path (they render at output resolution, where it is not visible).
4. **Shader reflection errors.** A constant buffer/sampler that the compiler optimized out cannot
   be bound (`Diligent could not reflect the static shader variable ...`). The final resolve shader
   is constant-free; a diagnostic tint proved the pass is in the frame.
5. **J2000 data errors.** A verification subagent compared the first-pass table with JPL Horizons
   DE441: Earth's mean anomaly was 1.10° off, Venus 0.33°, Neptune 0.63°, and Saturn's semi-major
   axis was 0.48% high. Corrected the table to the NASA mean elements; see the header comment.
6. **Build message: `'pwsh.exe' is not recognized`.** A subagent traced this to the user-wide
   vcpkg MSBuild integration (`C:\vcpkg\scripts\buildsystems\msbuild\vcpkg.targets`): it probes
   `pwsh.exe` first, prints the message, then falls back to `powershell.exe` and completes the
   app-local deployment. It is not repository code, the step is configured not to fail the build,
   and the executable is correct. Installing PowerShell 7 removes the message; no repo change is
   warranted.
7. **Shader ABI test stale hash.** `helios_shader_tests` failed until it was relinked against the
   rebuilt shader data; that is a build-order artifact, not a shader mismatch.

## Known limits / next

- No Saturn rings, moons, visible planetary atmospheres, or perturbations yet; the planet/ring
  code these need already exists in `planet_system.*` and `planet_sky.slang`.
- The Sun is an emissive photosphere with limb darkening, not a stellar-structure model.
- Supersampling offers 1x, 2x and 4x; 4x is four times the pixel cost of 2x and is not the default.
  A variable-factor resolve would need a working constant buffer (the constant-buffer binding was
  the source of issue 4).
- `homepage`/site gallery integration for the new captures is not done.
